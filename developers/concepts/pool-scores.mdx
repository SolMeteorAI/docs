## Rolling windows

Pool stats cover four rolling windows: `m5` (5 minutes), `h1` (1 hour), `h6` (6 hours) and `h24` (24 hours). Windows end at the newest data second, not the wall clock, so they never count a stretch with no indexed data as quiet.

| Field | Meaning |
| --- | --- |
| `volume_usd`, `buy_volume_usd`, `sell_volume_usd` | USD value of the window's swaps; buys and sells of the base token |
| `swaps`, `buys`, `sells` | Number of swaps |
| `makers`, `buyers`, `sellers` | Distinct wallets (approximate, within 0.1%) |
| `lp_fees_usd` | Fees paid to LPs |
| `avg_liquidity_usd` | Time-weighted average liquidity |
| `apr_pct` | `lp_fees_usd` ÷ `avg_liquidity_usd` × 100, scaled for pools younger than the window |
| `price_change_pct` | Change of the base token's USD price over the window |

<Warning>
  `apr_pct` is the yield **over the window**, not annualized. `apr_yearly_pct` is the 24-hour APR × 365.
</Warning>

For a pool younger than the window, rates are scaled by `k = window ÷ pool age`, so a 10-minute-old pool isn't compared on 10 minutes of fees against an hour.

## Fabriq score

`fab_score` ranks pools by recent LP opportunity: frequent swaps paying high fees against little liquidity. It combines the last 5 minutes (weighted 12×) and the last hour:

```text
fab_score = 100000 · ( 12 · (swaps₅ · k₅ / 5) · (fees₅ · k₅ / 5) / max(L₅, 1)
                     +      (swaps₆₀ · k₆₀ / 60) · (fees₆₀ · k₆₀ / 60) / max(L₆₀, 1) ) / 13
```

`swaps` and `fees` are the window's swap count and LP fees in USD, `L` its time-weighted average liquidity, and `k` the young-pool factor above. It is `null` while the pool's liquidity is unknown, and moves every second.

## 3-day LP score

`multiday.value_usd` answers: **what would 1,000 USD put into this pool as a full-range LP position 3 days ago be worth now, fees included?**

```text
V(t)   = 1000 · √(rx(t) · ry(t))           rx, ry: each token's USD price at t ÷ its price 3 days ago
fees   = Σ swaps  V(tᵢ) · feeᵢ / (Lᵢ + 1000)
score  = V(now) + fees
```

- 1,000 means break-even. The score is never negative, and a more profitable pool always scores higher.
- Each swap pays the position its share of the LP fee. Adding the position to the pool's liquidity `Lᵢ` stops a tiny pool from paying more than its own fees.
- Every pool is treated as full range. A tight range on a concentrated or bin pool earns more fees and suffers more impermanent loss than this; the score is the pool-wide average, comparable across pools.
- Pools younger than 3 days have no score.

Category tabs (`GET /trending/pools?category=equity`) sort by this score by default.

## Quality filter

`GET /trending/pools` lists only pools that pass the quality filter unless you pass `eligible_only=false`. `quality.eligible` on every pool says whether it passes.

A pool passes when its base token is **exempt**, or when it fails none of these checks:

| Check (`quality.failed`) | A pool fails when |
| --- | --- |
| `fdv` | Either token's FDV is under $50,000 (estimated FDVs count) |
| `holders` | Either token has fewer than 100 holders |
| `side_liquidity` | Either side of the pool holds less than $100 |
| `liquidity_cap` | The pool reports $1 billion or more of liquidity |
| `trading` | The base token has no organic score and its traders average more than 10 swaps each in 24 hours |
| `pumpswap_launchpad` | A PumpSwap pool's base token didn't come from pump.fun |
| `young_pool` | The pool is under a day old, and either its quote token has no organic score, or its base token is unverified, has no organic score, and its holder count × 2.5 exceeds its 24-hour traders |

Unknown values fail a minimum. A pool with no known creation date counts as old.

Exempt base tokens: launchpads `sunrise`, `prestocks`, `metadao` and `xstocks`, and the categories `bluechips`, `lst`, `stablecoin`, `equity`, `commodity` and `etf`.

<Note>
  Passing the filter doesn't make a token safe. It removes the most common kinds of noise from rankings.
</Note>
